# 10 · 数据模型

> 实现：[server/src/db.js](../server/src/db.js)（建表 DDL）、[server/src/serialize.js](../server/src/serialize.js)（字段转换）
> 数据库：SQLite 8（`better-sqlite3` 11.x，单文件库）

---

## 1. 总览

| 表 | 行数（生产） | 用途 |
|---|---|---|
| `users` | 1 | 账号 |
| `vehicles` | 2 | 车辆配置（含基线） |
| `sessions` | 22 | 充电记录 |

```
users ──1:N──> vehicles ──1:N──> sessions
  │                  │                │
  │                  └── M0 / R0 ──────┘（首段基线来源）
  └── id 用于所有表的 user_id 外键（数据隔离）
```

**级联删除**：`DELETE FROM users` 会连带删除其全部 vehicles 与 sessions。

## 2. 建表 DDL

```sql
CREATE TABLE IF NOT EXISTS users (
  id            TEXT PRIMARY KEY,
  email         TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  created_at    INTEGER NOT NULL DEFAULT (strftime('%s','now')),
  updated_at    INTEGER NOT NULL DEFAULT (strftime('%s','now'))
);

CREATE TABLE IF NOT EXISTS vehicles (
  id         TEXT PRIMARY KEY,
  user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  model      TEXT NOT NULL,
  B          REAL NOT NULL CHECK (B > 0),
  Pmax       REAL NOT NULL CHECK (Pmax > 0),
  M0         REAL NOT NULL CHECK (M0 >= 0),
  R0         REAL NOT NULL CHECK (R0 >= 0),
  color      TEXT,
  created_at INTEGER NOT NULL DEFAULT (strftime('%s','now')),
  updated_at INTEGER NOT NULL DEFAULT (strftime('%s','now'))
);
CREATE INDEX IF NOT EXISTS idx_vehicles_user ON vehicles(user_id);

CREATE TABLE IF NOT EXISTS sessions (
  id         TEXT PRIMARY KEY,
  user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  vehicle_id TEXT NOT NULL REFERENCES vehicles(id) ON DELETE CASCADE,
  ts         TEXT NOT NULL,
  E          REAL NOT NULL CHECK (E >= 0),
  T          REAL NOT NULL CHECK (T >= 0),
  C          REAL NOT NULL CHECK (C >= 0),
  M          REAL,
  R_start    REAL,
  R_end      REAL,
  meter      TEXT CHECK (meter IN ('battery','grid')),
  ctype      TEXT CHECK (ctype IN ('home','fast','other')),
  note       TEXT,
  created_at INTEGER NOT NULL DEFAULT (strftime('%s','now')),
  updated_at INTEGER NOT NULL DEFAULT (strftime('%s','now'))
);
CREATE INDEX IF NOT EXISTS idx_sessions_user          ON sessions(user_id);
CREATE INDEX IF NOT EXISTS idx_sessions_user_vehicle  ON sessions(user_id, vehicle_id);
CREATE INDEX IF NOT EXISTS idx_sessions_vehicle       ON sessions(vehicle_id);
```

> 建表在**模块 import 副作用**中执行（`index.js` 里 `import './db.js'`），无需迁移脚本。

## 3. users

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | TEXT | PK | UUID v4 |
| `email` | TEXT | **UNIQUE**、NOT NULL | 登录名，大小写敏感 |
| `password_hash` | TEXT | NOT NULL | bcrypt cost=10 |
| `created_at` | INTEGER | NOT NULL | Unix 秒 |
| `updated_at` | INTEGER | NOT NULL | Unix 秒 |

**要点**：
- 密码**永不明文存储**，也永不出现在任何 API 响应中
- `email` 唯一约束在 DB 层兜底，配合应用层查重（返回 409）
- 无「软删除」字段，删账号即彻底清除

## 4. vehicles

| 字段 | 类型 | 约束 | 单位 | 说明 |
|---|---|---|---|---|
| `id` | TEXT | PK | — | UUID |
| `user_id` | TEXT | FK → users(id), CASCADE | — | 归属账号 |
| `model` | TEXT | NOT NULL | — | 车型名，如「欧拉好猫21款波塞冬」 |
| `B` | REAL | NOT NULL, **CHECK > 0** | kWh | 电池容量 |
| `Pmax` | REAL | NOT NULL, **CHECK > 0** | kW | 最大充电功率 |
| `M0` | REAL | NOT NULL, **CHECK ≥ 0** | km | 初始里程基线 |
| `R0` | REAL | NOT NULL, **CHECK ≥ 0** | km | 初始车显剩余基线 |
| `color` | TEXT | 可空 | — | 车辆主题色（多车区分用） |
| `created_at` / `updated_at` | INTEGER | NOT NULL | Unix 秒 | |

### 4.1 M0 / R0 是什么

**首条记录没有「上一段」可参照**，需要用户提供基线：

| 字段 | 含义 | 正确取法 |
|---|---|---|
| `M0` | 开始用本工具记录之前，上一次充电**结束时**的里程表读数 | 翻历史记录或加油时的小票 |
| `R0` | 那时的车显剩余续航 | 当时的仪表盘照片 |

**填了** → 首条记录即可参与计算
**没填 / 填错** → 首条自动降级为「基准记录」（`baseline`），从第二条开始算

> ⚠️ 常见错误：把 `M0` 填成**当前里程**。这会导致 `dM = M − M0 ≤ 0`，首段被判定为基准。用户若看到首段不参与计算，先查这里。

### 4.2 CHECK 约束的作用

`B > 0`、`Pmax > 0`、`M0 >= 0`、`R0 >= 0` 是**数据库层兜底**。应用层 `validation.js` 也校验同样的规则，属于双重保障。

即使前端被绕过（如直接调 API），DB 也会拒绝非法值。

## 5. sessions

| 字段 | 类型 | 约束 | 单位 | 必填 | 说明 |
|---|---|---|---|:---:|---|
| `id` | TEXT | PK | — | ✅ | UUID |
| `user_id` | TEXT | FK → users(id), CASCADE | — | ✅ | 归属账号（冗余存储，便于直接按用户查） |
| `vehicle_id` | TEXT | FK → vehicles(id), CASCADE | — | ✅ | 归属车辆 |
| `ts` | TEXT | NOT NULL | — | ✅ | 充电时间，`YYYY-MM-DDTHH:mm` |
| `E` | REAL | NOT NULL, CHECK ≥ 0 | kWh | ✅ | 充电度数 |
| `T` | REAL | NOT NULL, CHECK ≥ 0 | h | ✅ | 充电时长 |
| `C` | REAL | NOT NULL, CHECK ≥ 0 | ¥ | ✅ | 金额 |
| `M` | REAL | **可空** | km | ❌ | 本次充电时的里程 |
| `R_start` | REAL | **可空** | km | ❌ | 充电时起始车显 |
| `R_end` | REAL | **可空** | km | ❌ | 充电结束车显 |
| `meter` | TEXT | CHECK IN (`battery`,`grid`) | — | ❌ | 度数口径 |
| `ctype` | TEXT | CHECK IN (`home`,`fast`,`other`) | — | ❌ | 充电类型 |
| `note` | TEXT | 可空 | — | ❌ | 备注 |
| `created_at` / `updated_at` | INTEGER | NOT NULL | Unix 秒 | ✅ | |

### 5.1 为什么 M / R_start / R_end 可空

这是**两阶段录入**的实现基础：

```
阶段一（充电当时，只记账单）  →  存 E / T / C / ts，里程车显留空
阶段二（回家后补录）          →  UPDATE 补 M / R_start / R_end
```

在补全之前，该记录被标记为 `pending`，不参与累计。补全后自动重算。

> 这是需求 §4.1「功能范围」的核心设计。详见 [01-产品需求 §2.3](01-产品需求.md)。

### 5.2 meter：度数口径 ⚠️

| 取值 | 含义 | 线损 |
|---|---|---|
| `battery` | 电池端 | 无 |
| `grid` | 电网端（含充电枪线损） | 约 10% |

**同一次充电，桩显示的度数是哪个口径，决定了后续所有计算**。电池端与电网端差约 10%。

**必须全程保持同一口径**，混用会导致电耗与效率测算失真。UI 在录入表单上有显式警示。

> 当前**不做**口径差异化建模（见需求 §4.2），只做「保持一致」的约束提示。

### 5.3 ctype：充电类型

| 取值 | 含义 | 用途 |
|---|---|---|
| `home` | 家充 | 分析页分组统计 |
| `fast` | 超充 / 快充 | 同上 |
| `other` | 其他 | 同上 |

**不影响任何电耗或均价计算**，纯粹是分析维度。

### 5.4 ts 是 TEXT 而非 INTEGER

存的是 `datetime-local` 输入框的原值格式（`2026-07-09T09:25`，**无时区**）。

**为什么不用时间戳**：
- 保留用户输入的原样，便于「两阶段录入」时修正
- 避免时区转换歧义（充电发生地就在本地，无跨时区需求）

**排序注意**：字符串格式固定长度，字典序 = 时间序，SQLite `ORDER BY ts` 可直接用。

> 潜在问题：如果将来接入不同格式的时区时间，排序会错乱。当前无此需求。

## 6. 索引策略

| 索引 | 覆盖查询 |
|---|---|
| `idx_vehicles_user` | `WHERE user_id = ?`（加载用户全部车辆） |
| `idx_sessions_user` | `WHERE user_id = ?`（加载用户全部记录） |
| `idx_sessions_user_vehicle` | `WHERE user_id = ? AND vehicle_id = ?`（**最常用**：当前车辆记录） |
| `idx_sessions_vehicle` | `WHERE vehicle_id = ?`（删除车辆前查记录数） |

> `sessions` 走 `user_id` 而非 `vehicle_id` 作为主要过滤条件，因为**每次打开应用都要加载当前用户全部记录**（多车切换场景下需要全量数据供前端 `computeAll` 一次性重算）。

**当前规模**（22 行）完全不需要索引优化，但索引已就位，便于未来增长。

## 7. ⚠️ 字段命名坑

**这是本项目最容易踩的坑。**

| 层 | 风格 | 示例 |
|---|---|---|
| 数据库表 | 下划线 | `vehicle_id`、`created_at` |
| **API 收发** | **下划线** | 同上（`serialize.js` 直接透传） |
| TypeScript | 驼峰 | `vehicleId`、`createdAt` |

**转换点**：

```ts
// server/src/serialize.js（后端 → API）
sessionRow(r) {
  return {
    vehicleId: r.vehicle_id,     // 下划线 → 驼峰
    createdAt: r.created_at,
    // 业务字段原样透传：E / T / C / M / R_start / R_end / meter / ctype / note
  }
}

// src/store/useAppStore.ts（API → store）
normSession(s) {
  return {
    vehicleId: s.vehicleId,
    createdAt: s.createdAt,
    R_start: s.R_start,          // 注意：这两个仍是下划线！
  }
}
```

### 7.1 ⚠️ `ChargeSession` 是混合命名

| 类别 | 字段 | 风格 |
|---|---|---|
| 系统字段 | `id`、`vehicleId`、`createdAt`、`updatedAt` | 驼峰 |
| **业务字段** | `E`、`T`、`C`、`M`、`R_start`、`R_end`、`meter`、`ctype`、`note` | **与 DB 一致**（含下划线） |

`R_start` / `R_end` 保留了**下划线**（`sessionRow` 显式写了 `R_start: r.R_start`），这是有意为之——它们本质是用户录入的「起止车显」两个独立值，不是同一实体的两个属性。

### 7.2 真实故障案例

用生产数据做本地 mock 时，直接把 DB 行喂给 store：

```js
// ❌ 错误：字段名不匹配
const SESSIONS = real.sessions
// → store.vehicles 正常，SESSIONS 全空，页面显示「0 条记录」
// → 容易误判为「布局坏了」

// ✅ 正确：显式映射
const SESSIONS = real.sessions.map(s => ({
  id: s.id, vehicleId: s.vehicle_id, ts: s.ts,
  E: s.E, T: s.T, C: s.C, M: s.M,
  R_start: s.R_start, R_end: s.R_end,
  meter: s.meter, ctype: s.ctype, note: s.note
}))
```

**排查提示**：如果 mock 数据下页面显示「0 条记录」，先检查 `vehicleId` 映射，不要急着怀疑前端逻辑。

## 8. 存储与运维

| 项 | 值 |
|---|---|
| 文件路径 | 容器内 `/data/ev.sqlite` |
| 环境变量 | `DB_PATH`（默认 `./data/ev.sqlite`） |
| 数据卷 | `xidu23okwlo2roftbhogivau_ev-data` |
| 模式 | WAL（`journal_mode = WAL`） |
| 容器重建 | 数据保留（卷挂载） |
| 单实例 | ⚠️ **必须**，多进程写会 `SQLITE_BUSY` |

⚠️ **WAL 模式下的备份**：直接 `cp ev.sqlite` 可能拿到不完整快照（`.sqlite-wal` 尚未 checkpoint）。用 `VACUUM INTO` 生成一致性快照。详见 [11-部署运维手册 §4](11-部署运维手册.md)。

## 9. 数据量与增长

| 场景 | 单车年记录数 | 单条约 200 B | 年增 |
|---|---|---|---|
| 每周充 1 次 | 52 | ~10 KB | 可忽略 |
| 每周充 3 次 | 156 | ~31 KB | 可忽略 |
| 每日充电（电摩） | 365 | ~73 KB | 可忽略 |

即使使用 10 年，100 辆车 × 每日充电也不过 ~270 MB。**SQLite 完全够用**，无需迁移。

## 10. 迁移注意事项

当前**无迁移框架**（建表用 `CREATE TABLE IF NOT EXISTS`）。

将来若需改表结构，建议引入 `user_version` 机制：

```js
// 伪代码
const v = db.pragma('user_version', { simple: true })
if (v < 1) { /* v1 迁移 */ db.pragma('user_version = 1') }
```

**注意**：SQLite 的 `ALTER TABLE` 能力有限（不能改列类型、不能删约束）。若涉及复杂结构变更，需「建新表 → 拷数据 → 删旧表 → 改名」。
