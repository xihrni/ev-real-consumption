# 14 · 已知问题

> 建档时点：2026-10-06
> 收录标准：**已知、暂不修、且有实际影响**的问题。已修的记在 [04-需求变更记录](04-需求变更记录.md)。

---

## 🔴 高优先级

### P1 · 无自动化测试

**现状**：`calc.ts` 是 123 行的纯函数，逻辑不复杂但**分支多**（4 种状态、5 个公式、多个边界），目前**零测试覆盖**。

**风险**：改算法时可能引入回归，而这类 bug 极隐蔽——数学上能算，结果却不合理（见 P2-1）。

**建议**：优先给 `calc.ts` 加测试，四个用例即可：

| 用例 | 断言 |
|---|---|
| 充满场景 | 自动退化为 `E ÷ dM × 100` |
| 部分充电场景 | `Econs < E`，不被高估 |
| 缺 `M` | 状态 = `pending`，不进累计 |
| `dM ≤ 0` | 状态 = `err` 或 `baseline` |

**当前进展**（2026-10-06）：`tsc --noEmit` 已修到 0 错误，可直接作为 CI 的第一道门禁。

**当前缓解手段**：每次发版前用**独立脚本**从生产库导出真实数据复算一遍（2026-10-05 已用过一次）。⚠️ 注意脚本**不能复用 `calc.ts`**，否则是自证。

---

### P2 · 无 CI

**现状**：构建、测试、发布全靠手工。

**风险**：
- 忘记跑 `tsc --noEmit` 就提交，类型错误留到运行时
- 忘记清 `dist/` 就发版，线上加载旧 chunk

**建议**：最少配一个 GitHub Actions，只做三件事：

```yaml
- run: npx tsc --noEmit
- run: npm run build
- run: ls dist/assets | wc -l    # 断言 == 2，防止残留
```

---

### P3 · git 未配置远程仓库

**现状**：`git init` 已做（2026-10-06），但**没有 remote**，只在本地。

**风险**：机器故障 / 误删磁盘 = 代码全丢。

**建议**：推到一个私有仓库（GitHub / Gitee 私有库）。

---

## 🟡 中优先级

### P4 · Service Worker 的 `controllerchange` 自动 reload

**现状**（`main.ts`）：

```ts
navigator.serviceWorker.addEventListener('controllerchange', () => location.reload())
```

**问题**：只要 SW 版本变更，**用户正在填的表单会立即丢失**。当前 SW 策略下触发不频繁，但用户若正好在录充电记录时遇到，会很恼火。

**缓解**：可考虑在有未保存表单时跳过 reload；或改为提示「有新版本，点击刷新」。

**未改原因**：当前触发条件明确（真发布才会变），优先级不高。

---

### P5 · ECharts 全量引入，JS 单包 1.19 MB

**现状**（`package.json`）：`"echarts": "^5.5.1"` 全量引入。

**影响**：gzip 后 398 KB，首屏解析约 100ms。已触发 `chunkSizeWarningLimit: 1500` 警告。

**优化路径**：改用按需引入 + 手动注册所需图表/组件，预计可减 600KB+。

**未改原因**：当前用户量小，1.19MB 在 4G 下也能接受。**但新增依赖前必须先做这件事**，否则雪球会滚起来。

---

### P6 · 报表表格列宽为固定比例

**现状**（`style.css`）：

```css
.rpt-table .rpt-head, .rpt-table .rpt-row {
  grid-template-columns: 1.4fr 0.7fr 0.9fr 0.9fr 0.9fr 1.1fr 0.9fr 0.8fr 0.8fr;
}
```

**问题**：9 列固定比例，**窄视口下会被 `text-overflow: ellipsis` 截断**。桌面已加宽到 13.5px 缓解，但平板竖屏（768px）下仍可能截断。

**改进方向**：窄屏改为卡片式布局（每行一「组」），或加横向滚动。

## 🟢 低优先级 / 已知取舍

### P7 · 车显数据质量无法自动校验

**现状**：算法层面，数学自洽的**不合理数据**会被正常采纳。

**真实案例**（2026-10-05 复算发现）：

```
第 5 段：dM = 148 km，但 dRdep = 38 km（车显只掉 38）
→ Econs = 4.31 kWh，real = 2.91 kWh/100km
→ 数学上自洽（dM>0, dR>0, dRdep>0），但结果远低于常识
```

**为什么系统不拦**：它无法区分「车显跳变」与「车机标定异常」。

**改进方向**（需权衡）：
- 加启发式：`real` 超出 [5, 60] 区间时给黄色警告（不阻断）
- ⚠️ 风险：会误伤电摩（4.6 kWh/100km 正常）

**当前结论**：保持不拦，靠用户看「表显 vs 真实」对比图自行判断。见 [03-数据采集规范 §4.4](03-数据采集规范.md)。

---

### P8 · `ts` 字段无时区信息

**现状**：`ts` 存 `datetime-local` 原值（`2026-07-09T09:25`），**不带时区**。

**风险**：若将来接入海外用户或跨时区数据，字符串排序会错乱。

**当前可接受**：用户在同一地充电，无跨时区场景。SQLite 排序依赖「定长格式 → 字典序 = 时间序」。

---

### P9 · 弹窗无焦点捕获

**现状**：
- ⬜ 弹窗打开时不锁定焦点（Tab 会跑到背景内容）
- ⬜ `Esc` 不能关闭弹窗
- ⬜ 图表无文字替代（屏幕阅读器读不到数据）

**影响**：无障碍体验不足。当前单人自用，影响有限。

---

### P10 · `emptyOutDir` 的沙箱兼容

**现状**（`vite.config.ts`）：

```ts
emptyOutDir: process.env.EV_KEEP_DIST !== '1'
```

**背景**：原本为 `false`，为绕开「沙箱 safe-delete 拦截 dist 删除」。已改为默认清空（解决 dist 累积 30 个 chunk 的问题）。

**残余问题**：受限沙箱环境构建时需 `EV_KEEP_DIST=1` 关闭，可能有人忘记。

**建议**：在构建脚本里加提示，或直接评估能否去掉这个兼容（服务器 Docker 构建本就不受沙箱影响）。

---

### P11 · 导出大数据量可能卡顿

**现状**：`exporters.ts` 一次性 `JSON.stringify` + `Blob` 下载。

**阈值估算**：1000 条记录约 200KB JSON，浏览器毫无压力；10 万条才会卡。

**当前可接受**：单人使用，几年内不会到那个量级。

---

### P12 · 无 E2E / 集成测试

**现状**：单元测试和 E2E 都没有。

**当前缓解**：每次发布后用 Playwright 手动跑 6 个视口截图核验（已形成流程，见 [06-响应式布局规范 §8](06-响应式布局规范.md)）。

**现状数据核验流程**（值得保留的实践）：

```bash
# 1. 从生产库只读导出真实数据
# 2. 用独立脚本重算（不复用 calc.ts）
# 3. 与页面显示值逐位比对
```

2026-10-05 用这个方法确认了 22 条记录的计算全部正确。
