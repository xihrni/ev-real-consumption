# 13 · 开发规范

> 约定优先于个人习惯。带 ⚠️ 的是**曾经出过 bug 的地方**。

---

## 1. 命名约定

| 类型 | 规则 | 例 |
|---|---|---|
| 组件文件 | PascalCase | `VehicleManager.vue` |
| 视图文件 | PascalCase + `View` 后缀 | `OverviewView.vue` |
| 工具/类型文件 | 纯小写 | `calc.ts` `format.ts` |
| 组合式函数 | `useXxx` | `useAppStore` |
| 类型/接口 | PascalCase | `ChargeSession` |
| 常量 | UPPER_SNAKE | `TOKEN_KEY` `CUR_KEY` |
| 布尔变量 | 无 `is`/`has` 前缀 | `loading` `editingId` |
| CSS 类 | kebab-case | `.warn-bar` `.card-title` |
| CSS 修饰类 | 语义名 | `.alt` `.on` `.active` |

### 1.1 ⚠️ 计算字段用数学符号命名

```ts
// src/types.ts —— 保留用户输入的原始符号，便于与公式对照
export interface ChargeSession {
  E: number          // 充电度数 kWh
  T: number          // 充电时长 h
  C: number          // 金额 ¥
  M: number | null   // 里程 km
  R_start: number | null
  R_end: number | null
}
```

**理由**：文档里的公式 `k = E / (R_end − R_start)` 与代码**逐字对应**，改代码时能立刻对照。

**代价**：`R_start`/`R_end` 保留了下划线，破坏了 TS 驼峰惯例。但换来的是可读性，接受这个不一致。

### 1.2 ⚠️ 混合命名是刻意的

| 类别 | 字段 | 风格 |
|---|---|---|
| 系统字段 | `id` `vehicleId` `createdAt` `updatedAt` | 驼峰 |
| 业务字段 | `E` `T` `C` `M` `R_start` `R_end` `meter` `ctype` `note` | 原始 |

**不要"为了统一"去改业务字段的名字**。它们与 DB 列名、CSV 表头、用户公式全部对齐，改动会牵连三处。

## 2. 数值安全 ⚠️⚠️ 最高优先级

### 2.1 ⚠️ `round()` 里的 `!isFinite` 是历史教训

```ts
// src/utils/format.ts —— 当前实现
export function round(n: number | null | undefined, digits = 2): number {
  // 注意：isNaN(Infinity) === false，必须额外用 isFinite 拦住 Infinity / -Infinity，
  // 否则除零结果会原样返回并污染「平均功率」「均价」等汇总指标。
  if (n == null || isNaN(n) || !isFinite(n)) return 0
  const f = Math.pow(10, digits)
  return Math.round(n * f) / f
}
```

**为什么 `!isFinite` 不能省**：

```js
isNaN(Infinity)            // false  ← 只判断 isNaN 拦不住！
isNaN(Infinity) || !isFinite(Infinity)   // true  ✅
```

**这个 bug 真实发生过**：`T = 0` 时 `E / T` 得到 `Infinity`，污染了「平均功率」统计。现在有两层防护：

```ts
// 第 1 层：算之前就不算
const power = cur.T > 0 ? round(cur.E / cur.T, 1) : null
//            ↑ T=0 直接给 null，不做除法

// 第 2 层：round 内部兜底
if (n == null || isNaN(n) || !isFinite(n)) return 0
```

**⚠️ 注意 `round()` 对非法值返回 `0` 而不是 `null`**。这意味着「无法计算」和「算出来是 0」在数值上无法区分。**所以不能用 `if (!power) 判断功率是否有效**，必须用 `power == null` 或 `power != null`。

```ts
// ❌ 错误：power 为 0（无效）时会被误判
if (seg.power) { /* ... */ }

// ✅ 正确
if (seg.power != null) { /* ... */ }
```

> 写新代码时若需要「无值」的语义，**用 `null` 显式表达，不要依赖 `round()` 的 0**。

### 2.2 除法前先检查分母

```ts
// ❌ 禁止
const price = segCost / dM * 100

// ✅ 分母在上游已保证 > 0，但要写注释说明依赖
const dM = cur.M! - prev.M!
if (dM <= 0) { /* 已在此处 return err */ }
const price = segCost / dM * 100     // 此时 dM 必然 > 0
```

**原则**：不是"到处加防御"，而是**在数据入口处拦截，在下游用类型系统和非空断言表达前提**。

### 2.3 三种状态的表达

| 状态 | 含义 | 表达方式 |
|---|---|---|
| **未填** | 用户没填这个字段 | `null`（不是 `0`！`0` 是有效值） |
| **算不出** | 填了但条件不足 | `null` + `status: 'pending'` |
| **无意义** | 条件不满足（如 `T=0` 的功率） | `null`（如 `power: null`） |

⚠️ **不要用 `0` 表示"没有数据"**。`M = 0` 是合法的里程（新车），`power = 0` 意味着"零功率"（插着桩没充）。

### 2.4 数组长度要防 0

```ts
const avgH = round(totalH / Math.max(durations.length, 1), 2)   // ✅
const avgH = round(totalH / durations.length, 2)                // ❌ NaN
```

## 3. ⚠️ 均价公式不可改回

```ts
// ✅ 现行（2026-09-18 起）
const segCost = cur.E > 0 ? cur.C * (Econs / cur.E) : 0
const price = (segCost / dM) * 100

// ❌ 禁止
const price = (cur.C / dM) * 100
```

**会导致 71.33 元/100km 的尖峰**。改之前必读 [08-算法原理 §4](08-算法-测算原理.md)。

## 4. 组件规范

### 4.1 展示组件不碰 store 写操作

```vue
<!-- ❌ 展示组件直接改 store -->
<button @click="store.deleteVehicle(v.id)">删除</button>

<!-- ✅ 上抛事件 -->
<button @click="$emit('remove', v.id)">删除</button>
```

**例外**：`SessionForm`（录入入口）直接调 store 是合理的。

### 4.2 弹层组件统一约定

```vue
<script setup>
// 父组件控制显隐，子组件只负责内容
const props = defineProps<{ open: boolean }>()
const emit = defineEmits<{ close: [] }>()
</script>
```

**理由**：弹层的 z-index、遮罩、滚动锁定都交给 `.mask` 样式统一管理。

### 4.3 ⚠️ 全局提示容器必须挂根级

```vue
<!-- App.vue -->
<template>
  <div v-if="!store.authReady" class="boot">…</div>
  <AuthView v-else-if="!store.authed" />

  <div v-else class="app-shell">
    …
  </div>

  <!-- ⚠️ 必须在根级，不在 v-else 里 -->
  <ToastHost />
</template>
```

**这个 bug 真实发生过**：`ToastHost` 只挂在已登录分支，登录失败时 `toast()` 无处渲染，用户点登录"完全没反应"。

**自检**：任何"提示/日志/上报"类能力，先问**它对所有分支都可达吗**。

### 4.4 图标用 lucide，不用 emoji

```vue
✅ <Zap :size="14" class="ic ic-brand" />
❌ <span>⚡</span>
```

理由：图标尺寸/颜色要跟设计系统联动，emoji 无法控制。

## 5. 样式规范

### 5.1 只在 `style.css` 写断点

```css
/* ❌ 组件内不写 */
<style scoped>
@media (min-width: 900px) { .chart { height: 300px } }
</style>

/* ✅ 集中管理 */
```

**理由**：断点散落会导致顺序冲突（`min-width` 越大越后写才赢，顺序一乱就失效）。

### 5.2 ⚠️ 改 `.content` 宽度要同步 Hero 变量

```css
:root { --hero-max: 760px; --hero-inset: 14px }
```

**公式**：`--hero-max = .content 的 max-width − 左右 padding 之和`

**漏改的后果**：Hero 卡与内容卡片左右边缘不齐（视觉上很明显）。

### 5.3 颜色只用变量

```css
/* ❌ */ color: #0fae8e;
/* ✅ */ color: var(--brand);
```

例外：`.stat.alt::before` 用了硬编码渐变（品牌→橙的语义渐变，无对应 token）。

### 5.4 新组件先想能不能复用

现有可复用件：`.card` `.stat` `.badge` `.tag` `.hint-text` `.warn-bar` `.empty` `.seg-control` `.btn-sec` `.btn-danger` `.icon-btn` `.sheet` `.mask`

**组合优先于新建**。

## 6. API 规范

### 6.1 后端错误信息必须可操作

```js
// ❌
res.status(400).json({ error: '参数错误' })
res.status(500).json({ error: '服务器内部错误' })

// ✅
res.status(400).json({ error: '记录参数不合法（ts 必填；E/T/C≥0）' })
res.status(400).json({ error: 'meter 取值不合法' })
```

**原则**：回答「**发生了什么 + 我该做什么**」。前端会直接展示给用户。

### 6.2 ⚠️ 所有数据接口必须按 `user_id` 过滤

```js
// ❌ 只按 id 查
db.prepare('SELECT * FROM sessions WHERE id = ?').get(req.params.id)

// ✅ 带上归属校验
db.prepare('SELECT * FROM sessions WHERE id = ? AND user_id = ?')
  .get(req.params.id, req.userId)
```

**越权风险**：不带 `user_id` 的话，改一下 URL 里的 id 就能看别人的数据。

### 6.3 用预编译语句

```js
db.prepare('SELECT * FROM vehicles WHERE user_id = ?').all(req.userId)   // ✅
db.prepare(`SELECT * FROM vehicles WHERE id = '${id}'`)               // ❌ SQL 注入
```

**注**：本项目所有 `user_id` 来自 JWT（非用户输入），注入风险低，但仍应保持预编译习惯。

### 6.4 校验双重保障

```
前端 validation.ts  →  交互体验（即时反馈）
后端 validation.js  →  API 契约（可被绕过）
DB CHECK 约束       →  最后兜底
```

**三层都要有**。前端校验可被绕过（直接调 API），DB 约束是最后防线。

## 7. 状态管理规范

### 7.1 能算就不要 watch

```ts
// ❌ 深比较整个数组
watch(() => store.allSessions, handler)

// ✅ 依赖 computed 缓存
const okSegs = computed(() => store.computed.segs.filter(s => s.status === 'ok'))
```

### 7.2 ⚠️ 命名别骗人

`persistCurrent()` 实际**只存当前车 id**（`localStorage['ev_current_vehicle_v1']`），不持久化数据本身。数据通过 API 立即落库。

**改名前先看实现**，别被名字误导。

### 7.3 写操作后调用 `persistCurrent()`

```ts
async addVehicle() {
  // ...API 调用...
  await this.persistCurrent()      // 记住选中的车
  toast('已添加车辆', 'success')
}
```

## 8. 提交前自检

```bash
# 一条命令跑完类型检查 + 单元测试
npm run typecheck && npm test

# 构建（CI 会断言 dist/assets 只剩 2 个文件）
npm run build && ls dist/assets
```

以上三项 CI 会自动执行（`.github/workflows/ci.yml`），本地跑一遍可提前发现问题。

仍需人工的部分（CI 覆盖不到）：

- 冒烟测试：至少 390 / 1024 / 1600 三个视口，见 [06-响应式布局规范 §8](06-响应式布局规范.md)
- 改动核心算法后用真实数据独立复算，见 §8.1

| 检查项 | 怎么验 |
|---|---|
| 类型无错 | `npx tsc --noEmit` |
| dist 无残留 | `ls dist/assets` 应只有 2 个文件 |
| 移动端没回归 | 390px 截图对比 |
| 桌面端正常 | 1600px 截图 |
| 控制台无警告 | Playwright 监听 `console` |
| 均价公式没被改 | 检查 `calc.ts` 是 `segCost` 版本 |
| 文案与实现一致 | 改动文案时同步核对行为 |
| 核心文档已同步 | 改了算法/接口/表结构 → 更新对应文档 |

### 8.1 ⚠️ 改了核心逻辑要独立复算

**用真实数据脱离 UI 跑一遍**（2026-10-05 的做法）：

```bash
# 1. 从生产库只读导出
node dump.mjs > /tmp/evdata.json

# 2. 用独立脚本重算（不复用 src/utils/calc.ts，避免自证）
node verify.mjs /tmp/evdata.json
```

**为什么不用 `calc.ts`**：如果 bug 就在 `calc.ts` 里，用它自己验证等于没验证。

## 9. 部署规范

**发布流程见 [11-部署运维手册](11-部署运维手册.md)，核心三条**：

1. **阶段顺序不可颠倒**：docker cp 注入 → 同步源码 → 重建镜像
