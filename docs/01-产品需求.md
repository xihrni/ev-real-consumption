## 1. 问题定义

### 1.1 用户当前的痛点

电动汽车的车机仪表盘会显示「剩余续航」，但这个数字**不可信**：

| 现象 | 实质 |
|---|---|
| 车显续航 300 km，实际只跑了 180 km 就趴窝 | 车显按理想工况估算，未考虑温度、载重、高速、空调 |
| 车显百公里电耗 13 kWh，实际加油/充电量算出来是 18 | 标定偏乐观，且累计误差不会自我纠正 |
| 不同充电桩显示的「充电度数」口径不一 | 有的是电池端，有的是电网端（含线损），差约 10% |
| 每次充电的账单只能看单次，算不出长期成本 | 缺少跨记录的归集与折算 |

**根本问题**：车机给的是**估算值**，且估算基准会随环境漂移。用户需要一个**基于实际充电量和实际里程**的真实电耗与成本。

### 1.2 现有方案的不足

| 方案 | 问题 |
|---|---|
| 看车机仪表盘 | 估算值，不可验证 |
| 用第三方能耗 App | 需要 OBD 硬件 / 车型适配，且无法覆盖两轮车 |
| 手动 Excel 记账 | 无法处理「部分充电」场景，公式极易写错 |
| 只看充电桩 App 的单次记录 | 缺少跨次归集，看不出长期趋势 |

## 2. 目标用户与场景

### 2.1 目标用户

| 优先级 | 用户画像 | 特征 | 占比预期 |
|:---:|---|---|---|
| **主要** | 新能源车主（私家车） | 有固定充电习惯，愿意记录，关心长期成本 | 80% |
| **次要** | 电动两轮车用户 | 铅酸电池、充电桩按时间计费、跨城骑行 | 20% |

**当前实际部署**：项目所有者一人使用，已录入 2 辆车（欧拉好猫 / 72V20Ah 电摩）、22 条充电记录。

### 2.2 核心使用场景

```
场景 A（主力，家充为主）
  晚上插枪充电 → 次日早上看账单，记度数+金额+时间
  → 周末出行前补一次里程和车显
  → 月末看「这个月我真实跑了多少、每百公里多少钱」

场景 B（次要，快充为主）
  高速服务区快充 → 立刻记一笔（只有度数/金额/时间）
  → 到家后补里程与车显（两阶段录入）

场景 C（电摩，按时间计费）
  充电桩只给「充电时长 + 金额」，不给度数
  → 需按 功率×时长 反算度数
  → 补录历史里程，得到真实电耗与均价

场景 D（多车）
  家里两辆车，周末交替开 → 切换当前车辆，分别统计
```

### 2.3 关键用户流程

#### 首次使用（一次性配置）

```
打开应用 → 注册账号
  → 添加车辆（车型名 / 电池容量 B / 最大充电功率 Pmax）
  → 配置基线 M0、R0（关键，见 §6.2）
  → 开始记录
```

#### 日常两阶段录入（核心流程）

```
阶段一：充电当时（30 秒）
  打开 App → 记：度数 E、时长 T、金额 C、时间
  → 提交（里程和车显可以留空）

阶段二：回家后（1 分钟）
  找到该条记录 → 点「补全 / 编辑」
  → 补：里程 M、起始车显 R_start、结束车显 R_end
  → 系统自动重算该段与所有累计指标
```

**设计要点**：阶段一是刚需（趁热记数据），阶段二是补充。若强制一次填完 6 个字段，用户在停车场根本做不到，会直接放弃。

## 3. 核心价值

| 价值 | 具体体现 |
|---|---|
| **真实** | 用实际充入电量 ÷ 实际里程，不信车机估算 |
| **可归因** | 部分充电场景下，准确区分「这一段实际消耗了多少电、花了多少钱」 |
| **成本可控** | 百公里均价直接对应真实花销，可用于评估电价合理性 |
| **零硬件** | 不需要 OBD、不需要车型适配，手机浏览器即可 |
| **多车通用** | 乘用车与两轮车同一套逻辑（充满自停场景自动退化为简单模型） |

## 6. 关键设计决策

> 记录**为什么**，避免后续迭代推翻。

### 6.1 为什么用电量代理法而非直接用电量

**问题**：充电桩给的「充电度数」是**本次补入的总电量**，而用户关心的是「这一段路消耗了多少电」。二者在部分充电场景下差异巨大。

**方案**：用车显续航变化作为「电量代理」——

```
k = 本次充入电量 E ÷ 车显续航增量 (R_end − R_start)
```

`k` 表示「每车显公里对应多少真实电量」，用它把「上一段消耗的车显里程」折算回真实耗电：

```
Econs = k × (上段结束车显 − 本段起始车显)
```

**收益**：同时兼容充满与部分充电。若直接用 `E ÷ dM`（充电度数除以里程），在「充了 50 度只跑了 30 km」的过充场景下会严重高估。

详见 [08-算法-测算原理](08-算法-测算原理.md)。

### 6.2 为什么基线要用户手动配置

首条记录没有「上一段」可参照，需要用户提供 **M0**（开始记录前那次充电结束时的里程）和 **R0**（当时的剩余车显）。

**取舍**：
- 让用户配 → 首条就能算出电耗，但填错会导致首段报异常
- 不让配 → 首条标为「基准记录」不参与计算，从第二条开始

当前实现是**两者都支持**：填了就用（首条即参与计算），没填或填错就自动降级为「基准记录」。这比强制要求更宽容。

### 6.3 为什么均价不能直接用金额除里程

**这是 2026-09-18 修复过的严重 bug，务必不要改回去。**

**错误做法**：`price = 本次充电金额 C ÷ 本段里程 dM × 100`

**问题**：当存在过充（充入电量远大于本段消耗）时，`dR`（车显增量）会远大于 `dRdep`（实际消耗的车显里程），导致算出的消耗被放大。实测出现过 **71.33 元/100km** 的尖峰（正常值域 14~22）。

**正确做法**：先算本次充电的单价，再按本段消耗占比分摊费用：

```
segCost = C × (Econs ÷ E)      ← 按消耗电量占比分摊
price   = segCost ÷ dM × 100
```

**这样做的额外好处**：电耗和均价用同一套建模口径，两者始终自洽——不会出现「电耗正常但均价离谱」的矛盾。

### 6.4 为什么采用全量重算

任意新增/编辑/删除后，对**所有段和累计指标**整体重算。

**取舍**：全量重算是 O(n)，n 通常是几十到几百条，性能无压力。相比增量重算，它彻底避免了「改了一条但后续统计没跟上」的累积误差——这是数据类应用最重要的正确性保证。

### 6.5 为什么桌面端用左侧导航

移动端底部 Tab 栏是拇指热区最优解；桌面端鼠标操作，底部栏会占据 68px 且不符合平台习惯，因此改为左侧竖排导航。详见 [06-响应式布局规范](06-响应式布局规范.md)。

## 7. 核心指标（用户侧）

| 指标 | 定义 | 用途 |
|---|---|---|
| 真实百公里电耗 | `Econs ÷ dM × 100` | 核心指标，判断车机标定偏差 |
| 百公里均价 | `segCost ÷ dM × 100` | 核心指标，判断用电成本 |
| 累计行驶 | `Σ dM` | 里程归集 |
| 累计花费 | `Σ segCost` | 费用归集 |
| 单位电价 | `Σ segCost ÷ Σ Econs` | 反推实际单价，用于校验充电桩计费是否合理 |

> **实测参考**（2026-10-05 复算 22 条记录）：
> 欧拉好猫累计 2841 km、20.97 kWh/100km、18.97 元/100km、539.02 元 → 隐含 **0.905 元/度**
> 电摩累计 124 km、4.6 kWh/100km、7.45 元/100km、9.24 元 → 隐含 **1.621 元/度**（按时间计费桩反推，符合预期）

## 8. 已知局限（诚实声明）

| 局限 | 影响 | 缓解 |
|---|---|---|
| 依赖车显续航数据准确性 | 车显漂移会传导到电耗结果 | 提示同条件录入；提供「表显 vs 真实」对比图供用户自行判断车机准不准 |
| 充电桩度数口径差异 | 跨桩混合计算会失真 | 表单强制标注口径并警示保持一致 |
| 历史数据补录需估算 | 精度受限 | 备注字段标注「推算」，界面上明示 |
| 无自动化测试 | 改动有回归风险 | 靠全量重算的幂等性 + 每次发布前的独立复算（见部署手册） |
| 单实例 SQLite | 不支持水平扩展 | 当前用户量无需扩展；`ecosystem.config.cjs` 已强制 fork 单实例 |
