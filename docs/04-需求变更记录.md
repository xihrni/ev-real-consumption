## 1️⃣ 立项：混合充电测算工具（2026-07）

**背景**：车机显示的续航与实际不符，需要基于真实充电量与里程重新计算。

**核心设计决策**：

| 决策 | 选择 | 理由 |
|---|---|---|
| 用什么当"电量代理" | **车机剩余续航（R）** | 唯一免费、每次充电都自动更新的车辆侧数据 |
| 怎么算 | `k = E ÷ ΔR` 后折算消耗 | 兼容部分充电，简单模型做不到 |
| 要不要硬件 | **不要** | 避免 OBD 成本与车型适配 |

**明确排除**：OBD 接入、电表差异化建模、异常阈值告警。理由见 [01-产品需求 §4.2](01-产品需求.md)。

## 2️⃣ 两阶段录入（2026-07）

**问题**：理想流程要求一次填完 6 个字段，但用户在停车场做不到。

**决策**：拆成两阶段。

| 阶段 | 字段 | 时机 |
|---|---|---|
| 一 | `E` `T` `C` `ts` | 充电当时（30 秒） |
| 二 | `M` `R_start` `R_end` | 回家后（1 分钟） |

**实现**：DB 中 `M`/`R_start`/`R_end` 允许为 NULL，缺失时记录标记 `pending` 排除出累计。

**影响**：这个决策直接决定了 `sessions` 表的可空列设计。**改数据模型时不要把它们改成 NOT NULL。**

## 3️⃣ 首段「基准记录」容错（2026-08）

**问题**：首条记录缺 `M0`/`R0` 时算不出来，容易让用户卡住。

**决策**：**不强制用户配基线**，而是自动降级。

```
首条无有效基线 → 标记 baseline → 只建立起点，不参与计算
从第二条开始 → 正常测算
```

同时保留"填了就能算"的路径——用户配了 `M0`/`R0` 就直接用，首条也参与计算。

**结果**：新用户零配置即可开始使用，填错基线也不会损坏数据。

## 5️⃣ ⚠️ 均价公式修正（2026-09-18）· 最重要的变更

**症状**：用户截图反馈首页均价图有 **71.33 元/100km** 的尖峰，而正常值域是 14~22。

**排查过程**：

```
1. 用 headless Chrome 实测 → 确认服务端代码已是新版（bundle 命中 segCost 10 处）
2. 用截图旧曲线逐点比对「旧公式」→ 19 点全部吻合
3. 结论：浏览器缓存了旧版 bundle
```

**根因（两层）**：

| 层 | 问题 |
|---|---|
| **算法** | 旧公式 `price = C ÷ dM × 100` 用的是**整包充电费**。在过充场景（充 50 度只消耗 16 度）下，费用被放大 3 倍以上 |
| **缓存** | Service Worker "缓存优先 + 版本号永不变"，导致修复无法送达用户 |

**公式变更**：

```js
// ❌ 旧
price = C ÷ dM × 100

// ✅ 新
const segCost = C × (Econs ÷ E)     // 按消耗电量占比分摊
const price   = segCost ÷ dM × 100
```

**附带收益**：电耗与均价用同一套建模口径，两者永远自洽，不会出现"电耗正常但均价离谱"。

**验证**（2026-10-05 独立复算 22 条数据）：

| 车 | 隐含单位电价 | 合理性 |
|---|---:|---|
| 欧拉好猫 | 0.905 元/度 | ✅ 家充+快充混合的典型值 |
| 电摩 | 1.621 元/度 | ✅ 与按时间计费反推的 1.62 元/度吻合 |

> **⚠️ 此决策必须保留**。详见 [08-算法原理 §4](08-算法-测算原理.md)。改之前务必先读那一节。

## 6️⃣ Service Worker 缓存策略重写（2026-09-18）

**根因**：旧 SW 缓存优先 + `ev-cache-v2` 版本号永不更新，用户几个月看不到新版本。

**新策略**：

| 资源 | 策略 |
|---|---|
| HTML 导航 | **网络优先** |
| `/api`、`sw.js` | 永远走网络 |
| 静态资源 | stale-while-revalidate |

**配套**：`express.static` 发 `no-cache, no-store, must-revalidate`；`main.ts` 监听 `controllerchange` 自动 reload。

> **教训**：SW 的版本号策略必须与发布流程一起设计，否则会持续产生"改了但用户看不到"的问题。

## 8️⃣ 新增电摩支持（2026-10-02）

**背景**：用户有辆电动摩托车（72V20Ah 铅酸），问是多少度电。

**计算**：`72V × 20Ah = 1440 Wh = 1.44 kWh`（电池标称）

**但实际满充从市电取电 ≈ 2.2~2.4 度**（铅酸需 120~140% Ah 输入）。这个物理常识验证了后续推算的可信度。

**历史记录填报**：3 笔充电桩订单只给「时长 + 金额」，无度数。

| 决策 | 选择 |
|---|---|
| 推算方法 | `度数 = 功率 × 时长`，功率按 `0.29 kW`（= 289W）经验值 |
| 车辆配置 | `B=1.44`、`Pmax=0.29`、`M0=0`、`R0=60` |
| 里程估算 | 已知总里程 144km、距上次充电 20km → 分配为 51/97/124 |
| 标注 | `note` 统一写「由充电桩功率×时长推算」 |
| 授权 | 用户选择「帮我直接录进去」（AI 代填） |

**验证**：

| 记录 | 时长 | 金额 | 推算度数 | 桩单价 |
|---|---:|---:|---:|---:|
| 1 | 8.15 h | 3.83 元 | 2.36 | 0.470 元/h |
| 2 | 7.24 h | 3.38 元 | 2.11 | 0.467 元/h |
| 3 | 4.25 h | 2.03 元 | 1.23 | 0.478 元/h |

折算单价 **1.62 元/度**，与实测累计电费 9.24 元 ÷ 5.69 度 = 1.624 元/度 完全吻合。

**结论**：充满自停场景下 `R` 常量在公式中被约掉，退化为 `real = E ÷ dM × 100`。**电摩只需填对 E 和 M。**

## 9️⃣ 破坏性操作加三重防护（2026-10-05）

**背景**：审查「数据」页文案时发现严重问题。

**根因**：`loadDemo` / `importData` / `clearAll` 在 store 里都是**整库覆盖**（`replaceAll` 语义），但界面上「载入示例数据」与「导出 JSON」**长得一模一样**，点一下全部数据就没了。

**修复**：

| 层 | 措施 |
|---|---|
| 事前列示 | 顶部橙色 `.warn-bar` 点名三个破坏性操作 |
| 事中确认 | `confirm()` 三段式文案，**带当前实际条数** |
| 事前拦截 | 导入时先解析校验，缺 `vehicles` 明确报错 |

**同时修正的过时文案**：

| 位置 | 改动 |
|---|---|
| 「隐私说明」 | 「不联网不上传」→「随账号保存在服务端，需登录才能读写，不同账号隔离」 |

## 🔟 PC 端布局重构（2026-10-05）

**症状**：用户两次反馈——先说「PC 端显示手机布局」，改完说「还是有点小」。

**第一次改造**（2026-10-04）：加宽容器 + 底部 Tab 改左侧栏。

**第二次改造**（2026-10-05）：意识到「不是加宽，是整体尺度没放大」。

| 项 | 第一次后 | 第二次后 |
|---|---|---|
| 侧栏 | 232px | 248px（1440+ 268px） |
| 内容区 | 1040px | 1280px（1440+ 1616px） |
| 统计数字 | 23px | 27px（1440+ 30px） |
| 卡片标题 | 16px | 17.5px（1440+ 19px） |
| 图表高 | 300px | 340px（1440+ 400px） |
| 断点数 | 2 | 3（新增 1440px 超宽档） |

**关键认识**：**放大不能只改容器宽度**，字号、间距、图表高度要按信息层级同步调整，否则大屏上仍是"小字挤在大框里"。

**字号分级策略**：数字/标题放大 30%、导航 41%、正文 0%（保持 15px）、辅助 8%。

**移动端零回归**：所有放大规则都在 `min-width: 900px` 内。

## 1️⃣1️⃣ 登录页白字看不清（2026-10-05）

**症状**：用户截图反馈登录页顶部图标和标题"看不清"。

**根因**：

```
.auth-hero  { color: #fff }              ← 白字
图标        color="#fff"                   ← 白图标
.auth-wrap  { }                           ← ❌ 没有任何背景
body        { background: var(--bg) }     ← #f3f6f5 浅灰
```

白字白图标落在浅灰上 = 白上加白。图标还是「白描边 + 18% 半透明白底」，几乎不可见。

**有趣发现**：`:root` 里定义了 `--bg-grad`（品牌渐变），但**全项目从未引用**——写了没用上的遗留变量。

**修复**：

| 项 | 改动 |
|---|---|
| `.auth-wrap` | 加 `min-height: 100vh` + `background: var(--brand-grad)` |
| 模板 | 新增 `.auth-inner` 分离容器与内容居中职责 |
| 图标 | 22→26px，底色提到 `.22` + 白色描边 + `drop-shadow` |
| 副标题 | `opacity: 0.9` → `color: rgba(255,255,255,.95)` |
| 卡片阴影 | 灰黑 → 绿调 `rgba(9,68,55,.22)` |
| 桌面端 | flex 居中，标题 25px、Logo 62px |

**同时修复**：`<meta name="apple-mobile-web-app-capable"> is deprecated` 警告 → 补标准 `mobile-web-app-capable`。修复后 6 视口跑完，**console warning 归零**。

## 1️⃣4️⃣ 分析页新增「单次充电分析」（2026-10-13）

**背景**：分析页原本只有 2 张图（各类型平均电价、月度趋势），粒度偏粗——只能看「按月」「按类型」的汇总，看不到**单次**的波动与异常。

**调研方法**：先拉生产数据看分布，再判断哪些维度做得出来。23 条记录的画像：

| 维度 | 分布 | 结论 |
|---|---|---|
| 车辆 | 欧拉 20 / 电摩 3 | — |
| ctype | fast 20 / other 3 / **home 0** | ⚠️ 见下 |
| meter | grid 23/23 | 口径统一，无需差异化建模（印证早期决策） |
| 月份 | 7月4 / 8月8 / 9月8 / 10月4 | 够画趋势 |
| 时段 | 78% 集中在 8–10 点 | 太集中，时段分布图价值低 |

**新增三张图**：

| # | 图表 | 关键设计 |
|---|---|---|
| 1 | 单次真实电耗散点 | 叠加**均值虚线 + ±1σ 常态带**（`markLine` + `markArea`），越界即偏离常态 |
| 2 | 车显标定漂移 | 画 `disp`（车显口径）趋势，**整体上移 = 车显越来越虚** |
| 3 | 电耗 vs 单段里程 | 揭示「短段对车显误差最敏感」，兼作数据质量体检 |

**技术要点**：
- 三图 Y 轴均设 `scale: true` —— 电耗值域在 15~24，从 0 起会把波动压扁成直线
- 图3 的 `grid.bottom` 需 ≥42，否则 X 轴标题被挤掉
- 桌面端图1 跨两列（`grid-column: 1/-1`），图2/图3 并排

**实测数据支撑**（决定了这三张图值得做）：
- `k` 值波动 **0.1032 ~ 0.1329（29%）**，漂移趋势明显
- dM 与 real **正相关**：短段(<100km) 16.7 / 中段 20.7 / 长段(≥200km) 21.8
  —— 反直觉，实为 #10（dM=18）和 #17（dM=17）两条**车显数据有问题**导致折算偏低

**⚠️ 调研中发现的遗留问题（同日已修）**：现有「家充 / 超充分组」名不副实 —— 家充 **0 条**，而那 3 条 `other` 恰好全是电摩，20 条 `fast` 全是欧拉。**该分组实际等价于「按车辆分组」**。

当日采用**方案 B** 修复：卡片加渲染门槛 `v-if="byType.length >= 2"`，类型少于 2 类时整卡隐藏。家充数据出现后会自动回归，无需再改代码。详见 [14-已知问题 P13](14-已知问题.md)。

**明确不做**（缺数据字段，非缺图表）：温度/季节影响、峰谷时段成本、电池衰减、单次充电功率曲线。
