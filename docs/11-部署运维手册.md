## 3. 标准发布流程（三段式）

> ⚠️ **顺序不可颠倒。** 第一步让改动立即生效，第三步保证重启后不回退。

### 阶段一：构建 + 注入运行容器（立即生效）

**目的**：镜像重建要 2-3 分钟，先让用户立刻看到新版本。

```bash
# 1. 本地构建（必须先清空 dist，否则残留旧 chunk）
cd /path/to/ev-app
rm -rf dist
node ./node_modules/vite/bin/vite.js build
# 验证：dist/assets 应只有 2 个文件
ls dist/assets

# 2. 上传产物
ssh root@47.121.185.253 "rm -rf /tmp/evdist && docker exec ev-app-xidu23okwlo2roftbhogivau sh -c 'rm -rf /app/dist && mkdir -p /app/dist'"
scp -r dist root@47.121.185.253:/tmp/evdist

# 3. 注入运行中的容器
ssh root@47.121.185.253 "docker cp /tmp/evdist/. ev-app-xidu23okwlo2roftbhogivau:/app/dist/ && rm -rf /tmp/evdist"

# 4. 验证
curl -s https://apc.llw2025.com/ | grep assets/
# 应看到新的 hash，且与 dist/index.html 中引用一致
```

> ⚠️ `express.static` 对 `index.html` / `sw.js` 设了 `no-cache, no-store, must-revalidate`，所以刷新即可拿到新版本，不需要绕缓存。

### 阶段二：同步源码（为镜像重建做准备）

**目的**：容器里的 `/app/dist` 是「外挂」的，一旦容器重建就没了。必须把**源码**同步到 `/data/ev-app`。

```bash
# 1. 打包源码（排除 node_modules / dist / .git）
cd /path/to/ev-app
tar -czf /tmp/evsrc.tgz src public server index.html Dockerfile \
  package.json package-lock.json vite.config.ts tsconfig.json .dockerignore
scp /tmp/evsrc.tgz root@47.121.185.253:/tmp/evsrc.tgz

# 2. 备份 + 覆盖
ssh root@47.121.185.253 "cd /data/ev-app && \
  BAK=/data/_bak_evapp_\$(date +%Y%m%d%H%M) && mkdir -p \$BAK && cp -r src \$BAK/src && \
  tar -xzf /tmp/evsrc.tgz -C /data/ev-app && echo EXTRACT_OK && echo \$BAK"
```

### 阶段三：重建镜像 + 重建容器

**目的**：让镜像与源码一致，保证下次重启不丢改动。

```bash
# 1. 后台构建（避免 ssh 等子进程结束被 SIGTERM）
ssh root@47.121.185.253 "cd /data/ev-app && rm -f /tmp/build.log && \
  (setsid docker build -t ev-app:1.0.0 . > /tmp/build.log 2>&1 < /dev/null &) ; sleep 3; echo STARTED"

# 2. 轮询等待（最长 7 分钟）
ssh root@47.121.185.253 "for i in \$(seq 1 40); do \
  if ! pgrep -f '^docker build' >/dev/null; then break; fi; sleep 10; done; tail -6 /tmp/build.log"

# 3. 用新镜像重建容器（走 Coolify 的 compose）
ssh root@47.121.185.253 "cd /data/coolify/services/xidu23okwlo2roftbhogivau && \
  docker compose up -d --force-recreate ev-app"

# 4. 验证
ssh root@47.121.185.253 "docker ps --filter name=ev-app-xidu --format '{{.Names}} {{.Status}}'; \
  docker exec ev-app-xidu23okwlo2roftbhogivau ls /app/dist/assets; \
  docker exec ev-app-xidu23okwlo2roftbhogivau ls -la /data"
curl -s -o /dev/null -w "%{http_code}\n" https://apc.llw2025.com/healthz
```

### 3.1 ⚠️ 远程构建的坑

| 坑 | 表现 | 正确做法 |
|---|---|---|
| `docker build &` 未真正后台 | ssh 等子进程结束，随即 SIGTERM | `(setsid docker build ... > log 2>&1 < /dev/null &)` |
| `pkill -f 'docker build'` 误杀 | **把自己的远程 shell 也杀了**，ssh 报 255 | 必须写 `pkill -f '^docker build'`（加 `^`） |
| Git Bash 缺 coreutils | `dirname/head/tail/grep: command not found`，管道不可用 | 改用「写脚本 → scp → docker cp → node 执行」 |

### 3.2 快捷脚本

服务器上已有 `/data/ev-app/update.sh`，封装了阶段三 + 健康检查。适合**源码已同步**、只想重建镜像的场景：

```bash

```

## 4. 备份与恢复

### 4.1 备份

SQLite 处于 WAL 模式，**直接复制 `.sqlite` 文件可能拿到不完整快照**。正确做法：

```bash
ssh root@47.121.185.253 "
  mkdir -p /data/backup-ev
  docker exec ev-app-xidu23okwlo2roftbhogivau \
    node -e \"const D=require('better-sqlite3');const d=new D('/data/ev.sqlite');d.exec(\\\"VACUUM INTO '/tmp/bk.sqlite'\\\")\"
  docker cp ev-app-xidu23okwlo2roftbhogivau:/tmp/bk.sqlite /data/backup-ev/ev-\$(date +%Y%m%d-%H%M).sqlite
  docker exec ev-app-xidu23okwlo2roftbhogivau rm -f /tmp/bk.sqlite
"
```

`VACUUM INTO` 会生成一个**已合并 WAL 的一致性快照**，比裸复制可靠。

### 4.2 恢复

⚠️ 恢复会**完全覆盖**现有数据。

```bash
ssh root@47.121.185.253 "
  docker cp /data/backup-ev/ev-20261001-1200.sqlite \
    ev-app-xidu23okwlo2roftbhogivau:/tmp/restore.sqlite
  docker exec ev-app-xidu23okwlo2roftbhogivau sh -c '
    rm -f /data/ev.sqlite /data/ev.sqlite-wal /data/ev.sqlite-shm &&
    cp /tmp/restore.sqlite /data/ev.sqlite &&
    rm -f /tmp/restore.sqlite'
  # 重启让 better-sqlite3 重新打开
  cd /data/coolify/services/xidu23okwlo2roftbhogivau && docker compose restart ev-app
"
```

### 4.3 用户侧备份（推荐）

应用「数据」页提供的 **导出 JSON** 是更安全的备份方式：

- 包含全部车辆与记录的**原始输入值**
- 存放在用户本地设备，不受服务器故障影响
- 可用「导入 JSON」整库恢复

## 6. 故障排查

### 6.1 SSH 连不上但服务正常 🔥

**最高频故障。**

**症状**：`ssh: connect to host 47.121.185.253 port 22: Connection timed out`，但 `curl https://apc.llw2025.com/healthz` 返回 200。

**根因**：**fail2ban 临时封禁了本机 IP**（多次 SSH 失败后触发）。

**处理**：
1. **不要慌**，先用 `ping` + `curl /healthz` 确认业务是否正常
2. 业务正常说明只是 SSH 被封，**等待约 10 分钟自动解封**
3. 或从另一台机器 / 换网络出口重连

```bash
# 诊断三连
ping -n 3 47.121.185.253
curl -s -o /dev/null -w "%{http_code}\n" --max-time 15 https://apc.llw2025.com/healthz
ssh -o StrictHostKeyChecking=no -o ConnectTimeout=12 root@47.121.185.253 "echo OK"
```

**预防**：脚本里用 ssh 时避免高频重试；连接池建议设长超时 + 退避。

### 6.2 页面还是旧版本

**排查顺序**：

| 检查项 | 命令 / 方法 |
|---|---|
| 线上 hash 是否更新 | `curl -s https://apc.llw2025.com/ \| grep assets/` |
| 容器内 dist 是否更新 | `docker exec ... ls /app/dist/assets` |
| 是否被 Service Worker 缓存 | 打开 DevTools → Application → Service Workers → Unregister |
| 强制刷新 | `Ctrl+Shift+R`（绕过缓存） |

`sw.js` 已改为**导航请求网络优先**、`/api` 与 `sw.js` 永远走网络，理论上不会卡旧版本。若仍卡，检查浏览器是否残留了旧版 SW。

### 6.3 构建失败：apt 阶段超时

**症状**：Docker 构建卡在 `apt-get update` 或 `apt-get install`，动辄 10 分钟。

**根因**：Debian 官方源在国内带宽极低（约 90 KB/s）。

**现状**：`Dockerfile` 已把源换成**中科大 USTC 镜像**（约 548 KB/s），apt 阶段从 143 秒降到 27 秒。

```dockerfile
RUN sed -i 's|deb.debian.org|mirrors.ustc.edu.cn|g; s|security.debian.org|mirrors.ustc.edu.cn|g' \
    /etc/apt/sources.list /etc/apt/sources.list.d/*.sources 2>/dev/null || true
```

npm 源用 `registry.npmmirror.com`。**若将来又变慢，优先换源，不要加 `sleep`。**

### 6.4 dist 目录堆积旧 chunk

**症状**：`dist/assets` 里有几十个文件，镜像层虚增。

**根因**：历史上 `vite.config.ts` 设为 `emptyOutDir: false`（为绕开沙箱的 safe-delete 拦截）。

**现状**：已改为环境变量控制，默认清空：

```ts
emptyOutDir: process.env.EV_KEEP_DIST !== '1'
```

受限沙箱环境可临时 `EV_KEEP_DIST=1 npm run build` 关闭。

### 6.5 容器起不来

```bash
# 1. 看退出原因
docker logs ev-app-xidu23okwlo2roftbhogivau --tail 50

# 2. 常见原因
#    - [fatal] 生产环境必须设置 JWT_SECRET → 检查 .env
#    - /data 不可写 → 检查卷权限
#    - 端口冲突 → docker ps -a 看是否有僵尸容器占 3000
```

### 6.6 数据库锁

**症状**：写入报 `SQLITE_BUSY`。

**原因**：better-sqlite3 是**同步单进程**库，多进程并发写会冲突。

**处理**：确认没有用 PM2 cluster 模式或起多个容器实例。`ecosystem.config.cjs` 已强制 `instances: 1` + `exec_mode: 'fork'`，**切勿改成 cluster**。
