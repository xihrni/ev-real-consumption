# 08 · 算法：测算原理

> ⚠️ **本文档是防误改的核心文档。** 算法涉及多个易错点，改动前必读。
> 实现文件：[src/utils/calc.ts](../src/utils/calc.ts)（123 行，纯函数）

---

## 1. 要解决什么问题

已知每次充电的**度数 E、金额 C、时长 T**，需要算出**这一段路实际消耗了多少电、花了多少钱**。

难点在于：**充入的电量 ≠ 消耗的电量**。

| 场景 | 充入 E | 实际消耗 | 差多少 |
|---|---|---|---|
| 充满跑完整段 | 50 kWh | 48 kWh | 差 2 kWh（充电损耗 + 保留） |
| 充满后只跑 1/3 电 | 50 kWh | 16 kWh | **差 34 kWh** |
| 部分充电（补 20 度） | 20 kWh | 5 kWh | **差 15 kWh** |

如果直接用「充入电量 ÷ 里程」，在过充场景下会**严重高估**（最差可达 3~10 倍）。

---

## 2. 核心思想：用车显续航作「电量代理」

### 2.1 为什么可行

车机显示的剩余续航 `R`（km）与剩余电量 `S`（kWh）之间，近似线性：

```
R = f(S)，且斜率 k 相对稳定
```

只要能求出「每个车显公里对应多少真实电量」，就能把车显里程的消耗折算回真实电量。

### 2.2 求斜率 k

一次充电补入 `E` 度电，车显从 `R_start` 涨到 `R_end`：

```
k = E ÷ (R_end − R_start)
```

`k` 的单位是 **kWh / 车显公里**，含义是「车显每显示 1 公里，实际消耗多少度电」。

> 注意：这是**本次充电期间的瞬时斜率**。电池健康度、温度、充电倍率都会让它波动，所以每条记录都独立算自己的 k，而不是全局固定值。

### 2.3 计算本段真实耗电

从上一段结束后开到本次充电开始，车显从 `prev.R_end` 降到 `cur.R_start`，这段消耗的车显里程是：

```
dRdep = prev.R_end − cur.R_start
```

折算回真实耗电：

```
Econs = k × dRdep
```

完整公式：

```
Econs = [E ÷ (R_end − R_start)] × (prev.R_end − R_start)
```

### 2.4 兼容两种场景

**场景一：充满（`R_end` 是满值）**

```
R_end = prev.R_end = Rmax
→ dRdep = Rmax − R_start
→ Econs = [E ÷ (Rmax − R_start)] × (Rmax − R_start) = E
→ 退化为「充电度数 ÷ 里程 × 100」
```

**场景二：部分充电（`R_end < Rmax`）**

```
Econs < E   按实际消耗折算，不会高估
```

这就是「兼容充满与部分充电」的含义——**同一个公式自动退化成两种行为**。

> 电摩场景（充满自停）同理：`R` 变化范围小（9~60），但因为充满自停时 `R_end` 恒为 60，斜率 k 在公式中被约掉，结果仍是 `real = E ÷ dM × 100`。

## 3. 五个输出公式

设某条记录的输入为：

| 符号 | 含义 | 来源 |
|---|---|---|
| `E` | 本次充入电量 kWh | 充电桩账单 |
| `T` | 充电时长 h | 充电桩账单 |
| `C` | 本次充电金额 ¥ | 充电桩账单 |
| `M` | 本次充电时的里程 km | 里程表 |
| `R_start` | 充电时起始车显剩余 km | 车机 |
| `R_end` | 充电结束时车显剩余 km | 车机 |
| `dM` | `M − prev.M` | 派生：行驶里程 |
| `dR` | `R_end − R_start` | 派生：车显增量 |
| `dRdep` | `prev.R_end − R_start` | 派生：消耗的车显里程 |

### 3.1 真实百公里电耗 `real`

```
real = Econs ÷ dM × 100
```

`Econs ÷ dM` 是每公里真实耗电，乘 100 换成百公里口径。

### 3.2 表显电耗 `disp`

```
disp = k × 100
```

即车机自己报的百公里电耗（由充电度数反推车显标定）。**用途：与 `real` 对比**——差值越大说明车机标定越不准或数据波动越大。

### 3.3 本段分摊费用 `segCost`

```
segCost = C × (Econs ÷ E)
```

**按本段实际消耗的电量占本次充电电量的比例，分摊本次充电费用。**

### 3.4 百公里均价 `price`

```
price = segCost ÷ dM × 100
```

### 3.5 平均功率 `power`

```
power = E ÷ T
```

`T = 0` 时置 `null`（除零会产生 `Infinity`，必须拦截）。

## 4. ⚠️ 均价口径：为何不能用整包费用除里程

### 4.1 这是已修复的 bug

**错误公式**（v1.0 早期版本）：

```js
price = C ÷ dM × 100          // ❌ 直接用整包充电费
```

### 4.2 为什么会出错

在过充场景下，`Econs < E`（充的 50 度只消耗了 16 度），但 `price` 却把**全部 50 度的钱**都算进了这 16 度的消耗里，等于把费用放大 3 倍以上。

**实测故障**（2026-09-18 修复前）：百公里均价曲线出现 **71.33 元/100km** 尖峰，而正常值域是 14~22。

根因推导：设充满时 `Rmax = 501`，某次 `R_start = 21`，则

```
k = E ÷ (377 − 21) = E ÷ 356
```

若误用「金额 ÷ 里程」，费用按整包计；若误用 `k × dM`，则会被 `dR ÷ dRdep` 放大。实测 19 条记录的旧公式曲线与截图尖峰逐点吻合，确认了这一点。

### 4.3 现行正确做法

```js
const segCost = cur.E > 0 ? cur.C * (Econs / cur.E) : 0
const price = (segCost / cur.dM) * 100
```

**核心思想**：先求本次充电的**单价**（`C ÷ E`），再乘以本段实际消耗的电量。

### 4.4 附带好处：口径自洽

`Econs` 与 `segCost` 用的是**同一个分母来源**（`Econs/E`），所以「电耗」和「均价」永远成比例，不会出现「电耗正常但均价离谱」的矛盾。

这在 2026-10-05 的 22 条数据复算中得到验证：欧拉车隐含单位电价 **0.905 元/度**（家充+快充混合的合理值），电摩 **1.621 元/度**（按时间计费桩反推的 1.62 元/度吻合）。

### 4.5 ❌ 不要改回去

如果有人认为「均价就是金额除里程更直观」，请先读这一节。正确做法是**在帮助页也说明清楚**（`HelpView.vue` 的「测算原理」卡片已按现行口径编写）。

## 5. 四种段状态

每条记录会被判定为以下四种状态之一。判定顺序**不可颠倒**。

```js
// src/utils/calc.ts 实际判定顺序
if (!hasCur)                    → 'pending'   // 缺里程/车显/度数
if (!hasPrev)                   → 'baseline'  // 首段无有效基线
if (i === 0 && dM <= 0)         → 'baseline'  // 首段基线不合理
if (dM <= 0 || dR <= 0 || dRdep < 0) → 'err'
else                            → 'ok'
```

| 状态 | 含义 | 是否参与累计 |
|---|---|:---:|
| `ok` | 数据完整且自洽 | ✅ |
| `baseline` | 只建立起点，不参与消耗计算 | ❌ |
| `pending` | 缺 `M` / `R_start` / `R_end` 任一项 | ❌ |
| `err` | 数据自相矛盾 | ❌ |

### 5.1 `pending` 判定条件

`hasCur = E != null && R_start != null && R_end != null && M != null`

四项缺一不可。**设计意图**：支持「两阶段录入」——充电当时只记账单，里程和车显回家后补。

### 5.2 `baseline` 判定条件

`hasPrev = prev != null && prev.M != null && prev.R_end != null`

首段用 `M0` / `R0` 作为基线（来自车辆配置）。若 `M0` 缺失，或填成了当前里程（导致 `dM <= 0`），则降级为基准记录。

**设计意图**：宽容。填错基线不会损坏数据，只是首条不参与计算。

### 5.3 `err` 三种情况

| 情况 | 判定 | 错误提示 |
|---|---|---|
| 里程未增加 | `dM <= 0` | 行驶里程未增加，请确认 M > 上段里程 |
| 车显未增加 | `dR <= 0` | 车显续航未增加，请确认 结束车显 > 起始车显 |
| 消耗为负 | `dRdep < 0` | 上段结束车显 < 本段起始车显，可能遗漏了中间充电记录 |

每种情况都会生成对应的 `why[]` 文案，在记录列表里直接展示给用户。

## 6. 累计指标

```js
cumM += dM;  cumE += Econs;  cumC += segCost     // 仅累加 ok 段

real  = cumE ÷ cumM × 100
price = cumC ÷ cumM × 100
```

**注意**：累计是「先加总再相除」，不是「各段结果求平均」。后者在里程差异大时会严重失真。

### 6.1 单位电价（派生指标）

```
单位电价 = cumC ÷ cumE
```

不在 UI 中直接展示，但可用于交叉校验：若算出的单位电价与实际充电单价差异过大，说明数据录入有问题。

---

## 7. 全量重算

```js
computeAll(vehicle, sessions) → { segs, cum, sorted }
```

**纯函数**：
- 输入：车辆配置 + 记录数组
- 输出：全部段 + 累计指标
- **不依赖 store、不发请求、不改状态**

每次增删改后 Pinia 的 `computed` 自动重新执行。好处：

| 特性 | 说明 |
|---|---|
| 幂等 | 同样的输入必得同样的输出，多次计算不累积误差 |
| 无状态漂移 | 不存在「改了 A 忘了更新 B」的问题 |
| 可独立验证 | 可脱离 UI 用真实数据跑一遍脚本对账 |
| 性能可接受 | n ≤ 数百条，单次计算 < 1ms |

## 8. 算例

用真实数据走一遍（2026-10-05 复算第 5 段，欧拉好猫）：

```
输入：
  上段：M=64562, R_end=279
  本段：E=29.51, T=1.13, C=26.44, M=64710, R_start=241, R_end=501

计算：
  dM    = 64710 − 64562 = 148
  dR    = 501 − 241     = 260
  dRdep = 279 − 241     = 38
```

> 注意 `dRdep = 38` 而 `dR = 260`，差得很远——说明**这次是充满，但车显从 279（未满）开始**，即上一段没充满。

```
  k     = 29.51 ÷ 260        = 0.1135  kWh/车显公里
  Econs = 0.1135 × 38        = 4.31    kWh
  real  = 4.31 ÷ 148 × 100   = 2.91    kWh/100km
```

⚠️ **这个结果看起来异常小**（2.91 kWh/100km 远低于正常值）。原因：`dRdep = 38` 说明车显从 279 掉到 241 只消耗了 38 公里车显，但实际跑了 148 km。

**这正是数据质量问题**：车显数据与里程不匹配（可能是车显没更新，或上段结束时车显被重置）。系统会把它标为 `ok` 但数值失真——因为从纯数学角度它自洽（`dM>0`、`dR>0`、`dRdep>0`）。

**处理建议**：遇到明显偏离常识的段，应检查车显数据是否有误，而非信任计算结果。这也说明**输入数据质量比算法更重要**。

## 9. 精度与舍入

```ts
// src/utils/format.ts
export function round(n: number | null | undefined, digits = 2): number {
  if (n == null || isNaN(n) || !isFinite(n)) return 0
  const f = Math.pow(10, digits)
  return Math.round(n * f) / f
}
```

**所有中间结果在写入前 `round()`**，避免浮点误差在界面上抖动。

**⚠️ 关键点一：`isNaN` 拦不住 `Infinity`**

```js
isNaN(Infinity)          // false —— 拦不住！
isNaN(Infinity) || !isFinite(Infinity)   // true  ✅
```

任何除法运算后都必须过 `!isFinite` 这关。历史事故：`T = 0` 时 `E / T` 得到 `Infinity`，污染「平均功率」统计。现已两层防护：

```ts
// 第 1 层：算之前就不算
const power = cur.T > 0 ? round(cur.E / cur.T, 1) : null

// 第 2 层：round 内部兜底
if (!isFinite(n)) return 0
```

**⚠️ 关键点二：`round()` 对非法值返回 `0`，不是 `null`**

这意味着「无法计算」与「算出来是 0」在数值上**无法区分**。因此判断有效性必须用：

```ts
if (seg.power != null) { /* ... */ }    // ✅
if (seg.power) { /* ... */ }             // ❌ 0 会被误判为无效
```

`calc.ts` 中所有可能「无意义」的输出（`power`、异常段的全部指标）都显式置 `null` 而非 0。
